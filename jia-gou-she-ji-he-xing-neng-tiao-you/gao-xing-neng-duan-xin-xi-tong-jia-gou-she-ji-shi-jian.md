# 高性能短信系统架构设计实践

企业级短信网关在集团级场景下一天要处理 **4 亿条短信**，峰值要求达到 **4 万 QPS（下发吞吐）**。要支撑如此体量，系统必须从架构设计、调度模型、队列与限流、协议层优化、资源利用等多方面综合设计。

下面从几个核心维度拆解：系统是如何做到的。

### 1. 对外请求设计：协议决定架构 <a href="#id-4ox6-1765273428894" id="id-4ox6-1765273428894"></a>

#### 1.1 异步半双工模型 <a href="#wfkv-1765273428896" id="wfkv-1765273428896"></a>

短信协议与常见的 HTTP 有明显差异。HTTP 是典型的同步请求-响应模式，每个请求都依赖调用栈等待结果返回；而短信链路采用 异步半双工机制，同一链路上可以连续发送多条短信，响应会在稍后以不确定顺序返回。

系统必须依赖 SequenceID / MessageID 进行请求-响应匹配，而不能使用阻塞式的同步方式。这种模型的最大优势是：链路的利用率更高，在高峰期不会被“同步等待”所限制。

#### 1.2 避免每个请求建一次链接 <a href="#qqfi-1765273428907" id="qqfi-1765273428907"></a>

TCP 建连成本包括三次握手、窗口探测和慢启动。在高并发场景（如数万 QPS）下，如果每条短信都重新建连，会导致：

* 大量 TIME\_WAIT
* 内核套接字资源耗尽
* 吞吐受制于慢启动
* 建连耗时成为主要延迟来源

因此必须使用：

* 长连接

通过连接复用显著降低系统开销，并保持链路的稳定吞吐能力。

***

### 2. 内部服务设计：数据结构决定性能 <a href="#id-5csx-1765273428930" id="id-5csx-1765273428930"></a>

#### 2.1 内存优先的数据校验 <a href="#id-5tcs-1765273428932" id="id-5tcs-1765273428932"></a>

短信系统的多数业务规则属于高频读数据，例如：接入号规则、路由规则、IP 鉴权、携号转网数据等。这些数据如果依赖数据库或 Redis，每次查询都需要 IO，将严重影响系统稳定性。因此，应将所有高频数据保存在内存中，初始化加载、定期刷新。

内存访问为纳秒级，而 IO 为毫秒级，两者之间有六个数量级的差距。

#### 2.2 数据结构与业务匹配 <a href="#ac55-1765273428942" id="ac55-1765273428942"></a>

结构选不对，性能就上不去。以下是短信网关的数据结构设计：

| 业务场景  | 特性        | 推荐结构                     |
| ----- | --------- | ------------------------ |
| 接入号匹配 | 前缀匹配      | Trie                     |
| 携号转网  | 拆分固定结构    | Off-Heap / Direct Memory |
| IP 鉴权 | 范围判断 + 有序 | 跳表                       |

合适的数据结构能显著减少CPU消耗，提高整体吞吐。

#### 2.3 避免无效内存拷贝 <a href="#id-1v9e-1765273429000" id="id-1v9e-1765273429000"></a>

短信数据在链路处理上会经过多次序列化与反序列化：接收 → 解析 → 构造下行 → 下发下游。

如果每一步都进行：

* byte\[] <-> String 转换
* ByteBuf → byte\[] 拷贝
* 大量临时对象创建

会导致显著的 GC 压力与 CPU 消耗。建议：

* 依赖 Netty 的 池化 ByteBuf
* 避免重复拷贝、避免中间结构拆装
* 采用 zero-copy 技术

最终目标是：减少分配、降低 GC、提升时延一致性。

#### 2.4 控制 GC 对延迟的影响 <a href="#mgej-1765273429028" id="mgej-1765273429028"></a>

Full GC 会带来数十到数百毫秒的 STW，对于高并发链路来说影响巨大。降低 GC 风险的策略包括：

* 避免频繁创建高频对象
* 使用对象池、缓冲区复用
* 避免不必要的 byte\[] 或 String 操作
* 使用 G1 GC 并设置最大暂停时间和合理的 Region 大小

GC 调优的目标不是“减少 GC 次数”，而是“降低 GC 对业务的影响”。

***

### 3. 异步化与稳定性设计：系统不能被下游拖死 <a href="#xtgk-1765273429045" id="xtgk-1765273429045"></a>

短信系统存在大量对外依赖（Redis、数据库、第三方短信网关），这些都是系统抖动的主要来源。因此，主业务链路必须保持 全异步化，并具备故障隔离能力。关键点包括：

* 异步处理主链路，不在业务线程中等待外部响应
* 所有外部调用必须设置超时
* 对失败场景实现可控重试
* 引入熔断机制，避免下游持续超时导致线程堆积
* 流量隔离，确保某个下游故障不会影响整体可用性

目标是：外部依赖抖动时，主系统仍能稳定运行。

***

### 4. 流量控制与队列管理：防止高峰期雪崩 <a href="#jcgz-1765273429067" id="jcgz-1765273429067"></a>

短信系统属于典型的“高峰明显”的业务。

在大促或关键时间点，流量可能瞬间暴涨，如果没有流控，将导致整个链路雪崩。系统需要具备：

* 全局限流
* 每个下游独立的发送队列
* 每个下游独立的限速器
* 队列满时立即返回错误，而不是继续堆积

拒绝比卡死更可控。“及时拒绝”是保证整体可用性的关键思路。

***

### 5. 框架与网络优化：基础能力直接决定上限 <a href="#cxs4-1765273429088" id="cxs4-1765273429088"></a>

网络层面建议采用 Netty，实现高效的多路复用和 I/O 处理。结合以下优化可以进一步提升系统性能：

* 使用池化 ByteBuf，减少对象分配
* 尽可能使用零拷贝技术

Linux 层面的 TCP 调优，包括：

* 调整 backlog
* 增大 socket 缓冲区
* 调整 TIME\_WAIT 管理
* 提高文件描述符限制
* 禁用 Swap，避免 Swap in/out 带来的不可预期延迟

网络层优化的目标是：更高的吞吐，更稳定的时延曲线。

***

### 6. 底层服务能力保障：防止被“短板链路”拖垮 <a href="#kklv-1765273429114" id="kklv-1765273429114"></a>

短信网关本质属于存储转发服务。在实际场景中，不同下游短信中心的能力差异巨大（有的上千 TPS，有的甚至不到百 TPS）。系统必须能够在下游能力不足时仍保持稳定。设计要点包括：

* 每个下游维护独立队列
* 队列满后立即拒绝，不继续积压
* 通过线程池隔离不同下游的处理
* 防止慢链路拖慢整个系统

最终保证：某个链路慢，不影响全局能力；系统不会被最弱的下游拖死。

***

### 总结 <a href="#wvrj-1765273429135" id="wvrj-1765273429135"></a>

短信系统的高性能不是依靠单点的“优化技巧”，而是由一系列架构原则共同保障的：

* 协议决定模型
* 数据结构决定性能
* 异步化决定吞吐
* 内存与 GC 决定稳定性
* 流控与隔离决定系统韧性
* 框架与网络决定上限
